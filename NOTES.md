## Decisions
- Claude Code is installed with `npm install -g @anthropic-ai/claude-code@$CLAUDE_CODE_VERSION` (pinned, system-wide, uses Debian nodejs/npm already required by the dashboard). The native installer was not used because it installs per-user and is harder to pin.
- s6-overlay tarballs are verified against the published `.sha256` files at build time. Arch chosen from TARGETARCH (amd64 -> x86_64, arm64 -> aarch64).
- Root filesystem is read-only (`S6_READ_ONLY_ROOT=1`); writable state is limited to tmpfs /run, /tmp and four named volumes.
- `dashboard/` (Step 2) only authenticates: login/logout, sessions, rate limiting, default deny, WebSocket upgrade guard (no WS endpoints yet). Listens on 0.0.0.0:7690 inside the container; published on host 127.0.0.1 only.
- One runtime dependency: `argon2`, pinned to exactly 0.43.1 (Argon2id is not in Node 20's stdlib). It ships glibc prebuilds for linux-x64 and linux-arm64 (node-gyp-build), so no compiler is needed on trixie. 0.43.1 pulls only @phc/format, node-addon-api and node-gyp-build. Why not 0.45.2: its prebuild targets a newer N-API than Debian trixie's Node 20.19.2 provides; loading it segfaults (exit 139), node-gyp-build then tries to compile, and the image has no make/g++. 0.44.x and later also add `cross-env` and its dependencies. Verified with Node 20.19.2 from trixie's apt (the image's Node, not Node 22): `require('argon2')` hash + verify works in `debian:trixie-slim`, and in the built image as user `web` (`docker build` of this repo succeeded, `npm ci --omit=dev` inside it). Do not switch the image to Node 22. Bumping argon2 needs a re-test with that command.
- The s6 `dashboard/run` now starts with `with-contenv` so `CCDASH_ORIGIN` from compose reaches the server. Not yet verified in a running container.
- `.dockerignore` excludes node_modules so a local install is not copied into the image.

## Dashboard auth (Step 2)
Env var: `CCDASH_ORIGIN` (Cloudflare origin, e.g. https://ccdash.example.com; set in .env, passed by compose, empty by default). http://localhost:7690 is always an allowed Origin.
State in /var/lib/ccdash-web: `auth.json` (0600, argon2id hash, username, generation = random nonce) and `sessions.json` (0600, SHA-256 of session ids). `ccd passwd` writes a new random generation and deletes sessions.json; the running server notices the new auth.json on the next request/30 s sweep, drops all sessions and closes registered sockets.
Assumptions:
- The `__Host-ccdash` cookie is `Secure`; browsers (Chrome, Firefox) accept Secure cookies on http://localhost, so the SSH tunnel http://localhost:7690 works. Not tested in a real browser yet. Safari is not assumed to work.
- The client IP is taken from CF-Connecting-IP when it is a valid IP, else the socket address; this is only safe because the port is reachable only via cloudflared and the loopback tunnel. Local processes in the container (ccd shares the network namespace) can connect directly and spoof it, so the per-client delay can be evaded. The global lockout (50 failures/hour, 15 min lock) still caps brute force at roughly 50 guesses/hour, and ccd can use the same lock to lock the owner out of the dashboard. Accepted for the MVP.
- ccd shares the container's network namespace, so it could bind port 7690 while the dashboard is down and serve a fake login page. Accepted risk for the MVP; mitigation: the dashboard must not crash (corrupt auth.json, socket errors and malformed requests are handled; s6 restarts it).
- Git tokens in /var/lib/ccdash-git/<owner> are readable by ccd by design (the credential helper runs as ccd). Use fine-grained, single-repo tokens with minimal permissions. The helper only answers for protocol https, host github.com and a plain owner name.
- Safari may not accept `Secure` `__Host-` cookies on http://localhost, so the SSH-tunnel route may not work there (use Chrome or Firefox, or the Cloudflare hostname).
- A corrupt, empty or malformed auth.json never crashes the server: at startup it behaves as "no password" (503, run ccd passwd), while running it keeps the previous credentials; both log one line without file contents and retry on the next request. A login whose password changes during verification is discarded (409, no cookie).
- Hardening: requestTimeout 10 s, headersTimeout 5 s, max header size 16 KB; Permissions-Policy, Cross-Origin-Opener-Policy and Cross-Origin-Resource-Policy headers; no HSTS (Cloudflare handles it, and localhost is plain http).
- `ccd-session start` passes the prompt after `--` to claude (claude 2.1.317 accepts `claude -- "-x"` as a prompt), and refuses to attach a project to an existing session of the same name that belongs to a different directory (a.b and a_b both map to claude-a_b).

- Rate-limit counters are in memory (reset on restart). Each login attempt counts as a failure while in flight and is refunded on success.
- Run `ccd passwd` needs a TTY; there is no non-interactive CLI mode (tests call `lib/authstore.setCredentials`).
- `ccd passwd` before the first start works; the server picks up auth.json without a restart.

### Hardening after review (server side)
- Directories ccd can write (`/home/ccd/.ccdash/agents`, `/run/ccdash/ops`, the transcript root) are read through `lib/safefile.js`: open with `O_NOFOLLOW|O_NONBLOCK`, `fstat` the descriptor, require a regular file, read through that descriptor. A FIFO, symlink or device named `*.jsonl`, `<id>.rc` or `<id>.log` is skipped (an `.rc` that cannot be read counts as "still running" until the timeout) instead of blocking the event loop. The transcript path is realpath-confined to /home/ccd/.claude first and then the realpath itself is opened (no check-then-reopen gap).
- tree.js reads at most the newest 200 `*.jsonl` files (by mtime), at most 512 KB each: a larger file is read from its tail (late stop/end events matter most) plus its first 16 KB (project, win), partial lines dropped. Parsed results are cached by (path, mtime, size). runOp reads `.rc` capped at 16 bytes (a bigger file is not a number) and only the last 4 KB of `.log`.
- `ccd-session` escapes a prompt (any argument) that ends in `;` as `\;`: tmux 3.5a treats a trailing `;` on an argv element as a command separator and silently drops it, while a trailing `\;` is a literal `;`. Checked byte for byte in a real tmux with a stub `claude` (scripts.test.js) for `;`, `\;`, `\\;`, newlines, `$()`, quotes and a leading `-`. An env var or temp file was not needed, because `-e VAR=...` is also an argv element and has the same trailing-`;` rule.
- Terminal WebSockets: the socket is registered with the session registry before `startSession` is awaited, so a logout or expiry in that window destroys it and it never gets a pty; `MAX_TERMS` (16) counts pending starts; a ws ping every 30 s terminates clients that miss a pong; after a terminal ends the `web-*` session is also killed by name (best effort, 1 s later).
- tmux denied (`access not allowed`) or unreachable (`error connecting`) now makes `/api/tree` and `/api/projects` answer 503 `{"error":"tmux unavailable"}` (logged once per outage) instead of showing every conversation as gone. Only `no server running` means "no panes".
- A clone that times out kills its `_ops` window (`new-window -P -F '#{window_id}'` gives the target) and removes its `.rc`/`.log`.
- Token files: a failed chgrp to ccd is logged (never the token), and the file's group and mode are checked before the rename; if it is not group-readable by ccd the request fails with 500.

### Known limitations (review follow-ups)
- Adding a project holds the HTTP request until the clone is done (up to 5 min). Cloudflare closes requests after about 100 s, so a clone that takes longer shows a 524 in the browser while it completes on the server. Opening the project afterwards works, because `ccd-project clone` is idempotent. The API contract is unchanged. A second request for the same repo while one is running shares the first call's result instead of queuing another clone when its prompt and token are identical (none and empty count as equal); with a different prompt or token it gets 409 `a request for this repo is already in progress with different settings`.
- The xterm `<style>` workaround in `public/terminal.js` patches `Document.prototype.createElement` (a `style` element becomes a hidden stub that writes through a constructable stylesheet) and `Element.prototype.setAttribute` for `style`. It is page-wide but only changes behavior for `style` elements and `style` attributes, which nothing else in the app creates. The alternative is to allow `style-src 'unsafe-inline'` in the CSP (simpler, weaker: it also permits injected inline styles); the shim was kept so the CSP stays strict.
- Terminals closed by a password change/logout see close code 1006 (registry destroys the socket) — cosmetic.

- Review fixes (server side): the tree parse cache keeps only the fields fold uses (cleaned, capped; at most 5000 events per file), a file over 512 KB is read as head plus tail without parsing the overlap twice, and the tail's first line is dropped only when it starts mid-line. `firstUserMessage` is cached by (path, mtime, size). A symlinked agents dir or transcript root is refused. tmux "access not allowed" is only recognised on stderr (or as the whole stdout), because stdout carries ccd-controlled text. A tmux `error connecting to <sock> (No such file or directory)` is deliberately not "no panes": it surfaces as 503 `tmux unavailable`. Stale `/run/ccdash/ops/<16 hex>.{rc,log,rc.tmp}` files older than 1 h are swept at startup and every 10 min. `ccd-session` drops an empty prompt. If attaching a terminal throws after the WebSocket upgrade, the socket is closed (no HTTP reject), the pty killed and the slot freed once. `dashboard/test` is removed from the runtime image (`rm -rf test` in the build stage); not run in the image.

### Copy and paste in the browser terminal
- tmux runs with `mouse on`, so a plain drag selects inside tmux (copy-mode). On release tmux copies to its buffer and sends an OSC 52 sequence to the client; `@xterm/addon-clipboard` 0.2.0 (served as `/assets/addon-clipboard.js`, global `ClipboardAddon.ClipboardAddon`) writes it to the browser clipboard. Applications in a pane that emit OSC 52 (with `set-clipboard on` / `allow-passthrough on`) reach the clipboard the same way.
- Shift+drag bypasses tmux mouse mode and uses the browser's native selection (copy with Ctrl+C / Ctrl+Shift+C or the context menu).
- Paste with Ctrl+Shift+V (browser paste into xterm) or the paste button on the terminal view.
- The clipboard API needs a secure context (HTTPS via Cloudflare or localhost) and a user gesture; the browser may ask for clipboard permission, especially for reads (paste button, OSC 52 queries). A refused write is silent.
- Verified on tmux 3.5a with `rootfs/etc/tmux.conf` and TERM=xterm-256color (the server's pty TERM): a copy-mode yank sends `ESC ] 52 ; ; <base64> BEL`. tmux leaves the selection parameter (Pc) empty, and the addon's default provider only writes when Pc is `c`, so the page must construct the addon with a provider that treats an empty Pc as `c`. An application's own `ESC ] 52 ; c ; ...` is forwarded unchanged. No tmux.conf change was needed.
- This deliberately supersedes the handoff's "no extra controls on the terminal view" rule, at the user's request.

## Handoff 2 Phase A: build-time checks (2026-11-05)
All measured on the host (tmux 3.5a, Docker 29.9.2 rootless, compose v5.6.1). Throwaway names `h2probe-*`, all removed afterwards.

### 1. Longest prompt as one argv element
Command shape: `tmux -S <sock> new-session -d -s X sh -c 'printf %s "$1" | wc -c > out' _ "$PROMPT"`, and the same with `respawn-pane -k -t base:0.0`. Bisected on the byte count that `wc -c` reports.
- new-session: 16,197 bytes accepted, 16,198 fails with `command too long`.
- respawn-pane: 16,184 bytes accepted, 16,185 fails with `command too long`.
- 32,000 and above always fail. The limit is tmux's own client-to-server message (about 16 KiB for the whole command: all argv words plus overhead), not the kernel. Kernel check without tmux: a 131,071-byte argv word works, 131,072 gives `Argument list too long` (MAX_ARG_STRLEN = 131072).
- Recommendation: cap the argv prompt at 8,000 BYTES (UTF-8 bytes, not characters), which leaves room for a longer command, cwd, flags and env words around it. Handoff 1's 4,000 can be raised to 8,000. Anything longer must not go through argv: start the pane with the REPL, then `load-buffer` + `paste-buffer -p` (check 2), then Enter.

### 2. paste-buffer -p is one bracketed paste

## Handoff 2 Phase E (backend part 1): usage gauges, token accounting, ccd-reader

### What was built
- `rootfs/usr/local/lib/ccdash/hooks/statusline.sh` (managed settings `statusLine`): writes `{sid, ts, rate_limits, cost, context_window, model}` to `~/.ccdash/usage/<session_id>.json` (umask 027, temp file + mv, 0640), then runs `$CCDASH_STATUSLINE_CMD` (payload on stdin) or prints `<model> · ctx <used_percentage or ?>%`. Never fails Claude. `CCDASH_HIDDEN=1` records nothing; `state.sh` and `agents.sh` also exit at once under it (that is what keeps the `/usage` helper Claude out of the tree). The tmux service forwards `CCDASH_STATUSLINE_CMD` from `/run/s6/container_environment` like `CCDASH_APPROVAL_WAIT`.
- s6 service `ccd-reader` (`rootfs/etc/s6-overlay/s6-rc.d/ccd-reader`, depends on init-ccdash; script `rootfs/usr/local/lib/ccdash/reader.js`, standard library only): runs as ccd, socket `/run/ccdash/reader.sock` 0660 ccd:ccd. One JSON object per line in, one out. Ops: `stat {path}`, `tail {path, bytes}`, `read {path, offset, length}` (length and tail capped at 1 MiB; data is base64 with `offset`, `length`, `size`, `inode`). Every path must be absolute, NUL-free, resolve with realpath to a regular file under `/home/ccd/.claude/projects/` (compared with a trailing separator, so `projects-evil` fails; a symlink out is refused; the final open uses O_NOFOLLOW|O_NONBLOCK and fstat). Errors are only `bad_path|not_found|not_regular|bad_args|bad_op|bad_request|too_large`; outside and missing both say `not_found`, and no error repeats a path. `CCDASH_READER_SOCK` and `CCDASH_READER_ROOT` override socket and root (tests); the s6 run script needs nothing from the container env.
- `dashboard/lib/reader.js`: socket client (one connection per call, 5 s timeout, errors `ReaderError{code}`; `unavailable` when nothing listens). Without a socket, `CCDASH_READER_DIR` makes it call the same `handle()` of reader.js directly on that directory (node tests, no s6).
- `dashboard/lib/usage.js`: freshest reading (by `ts`) that has a valid `rate_limits` wins; per window `{status:'ok', used_percentage, resets_at, countdown, ts, stale}` or `{status:'unknown'}`. Nothing is ever estimated. `stale` = the window's `resets_at` has passed since the reading. The statusline fixture (`tests/fixtures/2.1.317/statusline.json`, `"synthetic": true`) has the 2.1.317 `rate_limits` shape: `{five_hour:{used_percentage,resets_at}, seven_day:{...}}`, `resets_at` in unix seconds. No real capture of rate_limits exists yet; `ccd doctor --live` has to compare with a real `/usage`.
- `dashboard/lib/usage-fallback.js`: OFF unless `CCDASH_USAGE_FALLBACK=1` or the file `~/.ccdash/usage-fallback.enabled` exists (doctor --live will write it). Only runs when `/api/usage` finds no reading with rate_limits; starts `claude` with `CCDASH_HIDDEN=1` in a new window of `_ops` (`tmux new-window -e CCDASH_HIDDEN=1 -c /workspace`), types `/usage`, polls capture-pane, parses, sends `/exit`, kills the window. At most once per 10 min. `/usage` shows reset times as local text, so a fallback gauge has `resets_at: null`, `countdown: null` and `resets_text`. The screen format of the real 2.1.317 `/usage` is a guess (parser tolerant, covered by synthetic screens only) and the trust dialog for `/workspace` is not handled: unverified until doctor --live.
- `dashboard/lib/tokens.js`: reads each transcript through the reader by offset, keeping inode, offset and a carried partial line per file; resets from byte 0 when the inode changes or the size drops below the offset; only complete lines are consumed. Real transcripts (2.1.x, checked on live files) repeat an assistant message on one line per content block with the same `message.id`/`requestId` and the same `usage`, so a message counts once (if its usage differs between lines the last one wins). Subagent transcripts are separate files `<project>/<sid>/subagents/agent-<agent_id>.jsonl` (all lines `isSidechain:true`); the main file has none, so there is no double counting. The path comes from `agent_transcript_path` (SubagentStop only) and otherwise is derived from the conversation's transcript path (state record field `transcript`, now carried by `state.js`). Totals live in memory per file and are rebuilt from offset 0 after a restart; reads are throttled to one pass per 2 s and 32 MiB per file per pass. Views: epoch-aligned 5-hour windows (`floor(ts/18000)*18000`, not Claude's own reset-anchored window), project, conversation, model, agent. Prices (USD per million tokens, a small table by model family in `PRICES`: opus 5/25, sonnet 3/15, haiku 1/5; cache creation 1.25x, cache read 0.1x of input) are placeholders to edit; an unknown model counts tokens but no dollars and is listed in `unpriced_models`. Every payload carries `price_note: "API-price estimate, not billing"`.
- `process table`: `tmux.js` builds the parent -> children index once per `/proc` snapshot (cached on the table; `hasClaude` used to rebuild it for every pane of every conversation on each reconciler tick). `_stats.indexBuilds` lets the test count builds.
- `tree.js` nodes (conversations and subagents) now have `model`, `tokens` (null until the transcript was read), `transcript: {conv, agent}` and `elapsed` (seconds); `tokens.js`/`/api/tokens` refresh runs in the background of `/api/tree`.

## Handoff 2 Phase E (backend part 2): the `/events` WebSocket

`dashboard/lib/events.js`, wired in `app.js`. Upgrade at `/events` (GET) goes through the same `guardUpgrade` as `/term`: allowed Origin (else 403) and a valid session cookie (else 401), before the handshake; max 32 clients (503); sockets are in the `SocketRegistry`, so logout, expiry and password change close them. Ping every 30 s, a client that does not pong is terminated.

Triggers: `fs.watch(recursive)` on `~/.ccdash/` (if the directory is missing it retries every 5 s), debounced 100 ms, plus the reconciler tick (`CCDASH_RECONCILE_MS`, default 5000) as backstop. Each pass rebuilds the payloads and sends a type only when its fingerprint changed (clock-only keys `now`, `elapsed`, `countdown` are ignored). Nothing is computed while no client is connected. A new client first gets the last message of every type, then follows.

Server -> client (JSON text, one object per frame):
- `{type:'tree', tree:{now, projects:[...]}}`: exactly the body of `GET /api/tree` (without `?all=1`; "all time" still needs the HTTP call). Contains token totals, approvals, `elapsed`; `elapsed` is not re-pushed for clock alone, the browser keeps its own ticker.
- `{type:'state', states:{<sid>:{status, idle, quiet}}}`: reconciler status of every non-hidden conversation.
- `{type:'usage', usage:{...}}`: body of `GET /api/usage`.
- `{type:'tokens', tokens:{...}}`: body of `GET /api/tokens` (no `conversation` filter).
- `{type:'preview', id:<sid>, text}`: last lines of the pane, only for watched ids, only when the text changed, at most once per second per card per connection.

Client -> server: `{type:'watch', ids:[sid,...]}` (at most 50 per connection; ids that are not a UUID are ignored; the first preview follows at once) and `{type:'unwatch', ids:[...]}`. Anything else is ignored. Not covered by `/events`: `/api/projects` (no longer polled; refreshed on load and on user actions), "all time" tree, transcript view.

Tests: `dashboard/test/phase-e-events.test.js`.

## Phase F: egress
Files: `compose.egress.yaml` (an OVERRIDE, not standalone), `egress/` (proxy.js, allowlist.txt, Dockerfile), `host/ccdash-egress-allow`, `dashboard/lib/proxy.js`, `tests/stack/egress.sh` (+ `standin.js`), `dashboard/test/egress-proxy.test.js`.
- Turn it on with `docker compose -f compose.yaml -f compose.egress.yaml up -d --build`. It is off by default; `setup.sh` (Phase I) adds the second `-f` and `ccd doctor --live` appends hosts it saw denied. Nothing else in compose.yaml changes.
- ccdash moves to an `internal: true` network (`internal`) and loses its published port. The `egress` service sits on `internal` and `outside` (a normal bridge) and (a) is the HTTP CONNECT/HTTP proxy at `egress:3128`, (b) forwards its own `127.0.0.1:7690` to `ccdash:7690` (a published port on an internal-only container is dropped, Phase A check 3). So the host still reaches the dashboard at `127.0.0.1:7690`; the dashboard now sees the proxy container's address as the peer.
- Why a ~150-line node proxy instead of tinyproxy/squid: Phase A already proved this shape; it adds no new image family (base `node:22-slim` pinned by digest in `egress/Dockerfile`, nothing installed), no config language, a one-file allowlist that is re-read when it changes (no reload step), and one process that is both proxy and forwarder. It is unit-tested (`dashboard/test/egress-proxy.test.js`). Cost: it is our code, not a squid; it supports CONNECT and plain `http://` only, which is all git, npm, pip, curl and Claude Code use.
- Allowlist: `egress/allowlist.txt` (Anthropic API/login/telemetry hosts, github.com, api.github.com, codeload/objects, registry.npmjs.org, pypi.org, files.pythonhosted.org, fcm.googleapis.com, updates.push.services.mozilla.com, web.push.apple.com). Entries: `host`, `*.suffix`, `host:port`; a host with no port is allowed on 443 and 80 only. Extra hosts: `EGRESS_EXTRA_HOSTS` (comma separated, .env) or `host/ccdash-egress-allow <host>...`, which appends to `/data/extra.txt` in the proxy's volume (survives restarts; no reload, the proxy notices the mtime). `CCDASH_DOCKER` and `CCDASH_EGRESS_CONTAINER` (default `ccdash-egress`) select the engine and container.
- Log: every request is one line, `ALLOW host:port` or `DENY host:port`, in `docker logs ccdash-egress`. That is what doctor --live reads to find the hosts it needs to add.
- ccdash gets `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` (localhost, 127.0.0.1, ::1, egress) in both cases. s6 services do not inherit the container env, so `s6-rc.d/tmux/run` forwards just these six variables to the tmux server (and so to Claude, git, npm, pip, curl). Git over http reads the lowercase `http_proxy` only, hence both cases.
- Node's global `fetch` ignores the proxy variables: `lib/github.js` uses `lib/proxy.js` (`fetchViaProxy`: node:https with a CONNECT agent, no redirects, 1 MB cap) when `HTTPS_PROXY` is set. web-push gets its `proxy` option (it uses https-proxy-agent, already its dependency).
- Push endpoints (ALWAYS enforced, egress on or off): `https`, no credentials, default port, host exactly one of `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com`. Edge's `*.notify.windows.com` is not accepted by default (add it with `CCDASH_PUSH_HOSTS_EXTRA` and to the allowlist). `CCDASH_PUSH_HOSTS_EXTRA` (comma separated `host` or `host:port`, matched exactly) is for test stacks and unusual setups. Stored subscriptions with other hosts are dropped at load. This closes the Phase C SSRF note.
- The proxy resolves names itself, so an allowlisted name that resolves to a private address would be reachable; the allowlist is by name on purpose and the listed names are all public services.
- Limit: this stops stray traffic and a hijacked tool from phoning home to an arbitrary host. It does NOT stop Claude sending data to an allowed host: api.github.com, github.com (a push to a repo it controls), the npm and PyPI registries and the Anthropic API are all open by design.
- Test: `tests/stack/egress.sh` (stack `ccdashtest-egress`, port 7691, CI step in job `test`). Layers the real `compose.egress.yaml` on the test stack with a stand-in container (git over http, an https push endpoint) on the outside network only. Checks: `curl https://example.com` as ccd fails (proxied and unproxied) with a DENY line; the stand-in is reachable only through the proxy; add/pull through onboarding; a push send from the dashboard reaches the stand-in; vendor-only subscribe rules; `ccdash-egress-allow` takes effect with no restart; the loopback port works via the forwarder.

## Phase F: speed bumps
These slow down a careless mistake or a prompt-injected repo; they are not a security boundary (Claude still runs as ccd and can run anything not denied).
- Managed settings now carry `"permissions": {"deny": ["Bash(tmux:*)"]}`, so Claude's Bash tool cannot drive the tmux server (send keys to other conversations, read their panes). Phase H merges its `allow` for basic-memory next to it. Test: `tests/bats/statusline.bats`.
- Hook trust: a repo whose `.claude/settings.json` or `.claude/settings.local.json` has a non-empty `hooks` key, or any of `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `otelHeadersHelper`, non-empty `env`, `enabledPlugins`, `extraKnownMarketplaces`, `mcpServers`, or that has a `.mcp.json`, or whose `.claude`/settings files are symlinks (listed as `(symlink)`, checked with `git ls-tree` modes, never `git show` of the target) or unparseable (`(unparseable settings)`), is refused at onboarding unless trusted. Hooks run commands without asking, so a cloned repo could otherwise run code the moment Claude starts in it.
  - Where: `ccd-project` (called by `ccd-onboard`). Clone: checked right after `git clone`, before anything is recorded or started, and the new folder is deleted on refusal (it did not exist before). Pull: the upstream tree is read with `git show <upstream>:.claude/settings*.json` BEFORE the fast-forward, so the checkout is unchanged on refusal. Exit code 5, and one stdout line `hooks: Event,Event` (event names or the key names above only; the UI checkbox "I trust this repo's hooks" covers all of them, characters outside `[A-Za-z0-9_]` become `?`; commands are never printed).
  - Trust: `ccd-onboard --trust-hooks <owner/repo>` (host: `ccd clone --trust-hooks owner/repo`), or API `POST /api/projects` with `"trustHooks": true` (boolean; anything else is 400). A trusted onboarding stores `trustHooks: true` in `~/.ccdash/projects/<project>.json`, and later pulls of that project do not ask again. The UI shows "I trust this repo's hooks" only after a refusal, clears it when the repo field changes, and Pull on a card explains how to re-add.
  - API refusal: HTTP 409 `{"error":"repo-has-hooks","hooks":["PostToolUse","Stop"]}`, from both add and pull. The add path starts no session.
  - Not covered: hooks that come from a plugin, a skill's frontmatter, `~/.claude`, or a settings file Claude writes later (after trust). Settings with `hooks` as a non-object value count as hooks ("(unrecognised hooks value)").
- Managed `Bash(tmux:*)` deny is a prefix-match speed bump only: `env tmux`, `command tmux`, a script or a full path are not matched.
- With `totpRequired` set and nothing enrolled yet, anyone holding the password can enrol their own TOTP (the enrol route needs only the session); enrol right after setting the password.
- The egress proxy resolves names itself and, for plain HTTP, sends the allowlisted host as the outgoing `Host` header (not the client's). The 3128 listener binds all interfaces of the proxy container; the outside network is reachable from the host bridge only.

## Phase F: audit and sessions
Files: `dashboard/lib/audit.js`, `lib/sessions.js`, `lib/app.js` (sessions routes), `lib/api.js` (audit calls), `dashboard/test/audit-sessions.test.js`.
- Audit log: `/var/lib/ccdash-web/audit.log`, mode 0600, one JSON line `{ts, event, ...fields}`. Only whitelisted fields are written: `ip`, `outcome` (`ok`/`fail`/`enroll`), `reason` (a status code), `project`, `sid` (first 8 chars of a conversation id), `request` (approval id), `session` (16-char public session id). Unknown keys are dropped, so `prompt`, `text`, `input`, `token`, `secret`, `code`, `password` and the user agent can never be written; values must be short strings of `[A-Za-z0-9._:@/-]`.
- Events: `login`, `logout`, `auth.change`, `totp.change`, `totp.enroll`, `approve`, `deny`, `interrupt`, `close`, `wake`, `onboard`, `pull`, `token.saved`, `identity.change`, `session.revoke`, `session.revoke_all`. Prompts are not audited.
- Rotation: when a write would pass 10 MB, `audit.log` becomes `audit.log.1` and older files shift up; `audit.log.4` is dropped. So 5 files in total: `audit.log` plus `.1` to `.4`. Writes are synchronous appends.
- Sessions record `ip` (the existing `clientIp`: CF-Connecting-IP when valid, else the peer; with egress on the peer is the proxy container, no new trust) and `ua` (200 chars) at login.
- `GET /api/sessions` -> `{sessions:[{id, created, lastSeen, ip, ua, current}]}` (times in ms since epoch; `id` is the first 16 hex chars of the cookie's SHA-256, not the cookie). `POST /api/sessions/revoke {id}` -> `{ok:true, current:boolean}` (404 for an unknown id; the cookie is cleared when `current`). `POST /api/sessions/revoke-all` -> `{ok:true}` and clears the cookie. POSTs need an allowed Origin and `X-CCDash: 1`; an enrol-mode session gets 403.
- Revoking removes the session, destroys its sockets at once (terminals: the pty is killed and its `web-*` tmux session removed; `/events` closes), and drops its push subscription. A 2 s sweeper closes sockets whose session vanished anyway.
